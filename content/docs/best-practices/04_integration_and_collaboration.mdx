EC 固件很少独立交付——它总是嵌在客户的整机项目里，与 BIOS/驱动团队联调。本章约定协作时的接口、配置、调试与交付规范，减少"各改各的、临门对不上"的返工。

## 稳定的抽象接口（Abstraction Layer）

对上层主机（Host）隐藏底层差异，如：

```c
int ec_get_battery_status(struct ec_battery_info *info);
```

- 保持接口的前向兼容性：新增字段**追加在结构体尾部**，新增功能用新命令号，不改动旧字段语义。
- 接口带版本号：协议版本在握手阶段上报（如 `EC_CMD_GET_PROTOCOL_INFO`），客户可据此做能力协商。
- 破坏性变更走新接口：旧接口保留一个废弃周期，并在 changelog 里标注移除时间表。

## 配置管理协作

- 使用统一的 Kconfig + DeviceTree 配置模板，方便客户二次裁剪；
- 客户差异用**独立 conf 片段 + overlay**承载（`customer_x.conf`），主干共享——避免每个客户 fork 整个代码库（分层思路见[配置体系](/docs/development/architecture/05_configuration)）；
- 对共享资源（I²C 总线、Flash 分区、GPIO）定义**仲裁表**：哪个模块拥有哪个资源、谁可访问，写入项目 wiki 并随 PR 评审更新；
- 多项目共用的 `common/` 模块（charger、keyboard、thermal）只走主干，客户分支不做功能性修改、只做配置差异。

## 分支与发布

| 分支 | 用途 |
|------|------|
| `main` | 主干，所有功能开发合入点 |
| `release/x.y` | 发布分支，只接受缺陷修复 |
| `customer/x-项目名` | 客户项目分支：配置差异 + 客户节奏的验证 |

- 客户分支定期 rebase 到 release 分支，避免长期分叉；
- 每个 release 打 tag 并附 release note：变更点、已知问题、升级注意事项。

## 联合调试与问题定位

- 在集成阶段启用 Shell 命令接口，实时查看模块状态：

```
uart:~$ power status

uart:~$ battery info
```

- **问题单模板**（客户问题回传研发时必须齐全）：

| 字段 | 要求 |
|------|------|
| 现象 | 一句话 + 复现概率（如 3/10 次） |
| 复现步骤 | 从上电开始的完整序列 |
| 固件版本 | `kernel version` 输出 / 构建号 |
| 日志 | 事发时间段的串口/RTT 记录，标注时间点 |
| 波形 | 涉及总线问题时附逻辑分析仪截图 |
| 已排除项 | 已排查的方向（避免研发重复劳动） |

- 日志收集规范：客户侧抓日志统一用调高对应模块日志级别的方式（`log enable dbg <module>`），不用修改代码重编译；
- 跨团队问题（EC vs BIOS vs 驱动）先对齐**信号级证据**（波形、寄存器状态），再谈责任归属。

## 交付物清单

客户项目交付时，以下内容缺一不可：

1. 固件二进制 + 对应源码 tag（含 west manifest 锁定版本）；
2. 配置文件（conf + overlay）及说明；
3. Shell 命令清单（供客户产线测试使用）；
4. 已知问题列表与规避方案；
5. 升级说明（镜像、签名、回退方式）；
6. 本站对应章节链接（[烧录验证](/docs/getting-started/03_flash_and_verify)、[Bringup 清单](/docs/porting/07_bringup_checklist)）。

:::tip
协作问题的根因大多是"信息不同步"：接口变更没通知、配置改动没评审、日志没说清版本。把上面的模板变成团队习惯，比事后追责有效得多。
:::
